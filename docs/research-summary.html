Codex Sleep State Sugar 的研究成果、完整参数、实际实现、已验证边界，以及从长度分类迁移到 iPhone 17 质量闸门后的结论。

结论先行 当前代码不再用 292、312 或 780 的长度决定质量。隐藏探针只有在回答命中 iPhone 17、SSE 完整且 state 外层结构和签发时间有效时才缓存；iPhone 16、iPhone 15 或无法判定均拒绝。长度与块数只保留为诊断信息。
协议层出现了更重要的新证据 当前 OpenAI Codex 源码把 x-codex-turn-state 定义为“一个 turn 内”的粘性路由状态：同一 turn 的续传、重试和增量请求应原样回送；不同 turn 之间不应携带。CSSS 的跨新会话、跨 turn 复用属于实验性、非官方支持用法，并可能造成路由错误。

1. 我们到底观察到了什么

信号外层结构历史行为现在能下的结论
292 Base64URL 字符串 292 字符；解码后 217 字节；(217-57)/16 = 10 块 本机历史上曾采集并反复注入；用户的全新会话测试曾与正常质量结果相关 历史观测 是旧规则接纳的经验形状；不是 OpenAI 公布的质量等级
312 312 字符；233 字节；11 块 探针和正式响应都出现过；旧代码按块数拒绝，当前代码需结合探针回答判断 经验信号 与较差结果曾相关，但“撤销凭据”的含义没有公开协议证明
780 780 字符；585 字节；33 块 近期在多个模型请求中重复出现；旧规则拒绝，当前规则可在 iPhone 17 探针中接纳 当前观测 与固定长度填充或载荷扩张一致；无法从密文外形区分两者

这里的 292、312、780 是 x-codex-turn-state 请求头值的字符串长度，不是 HTTP 状态码。我们实际抓到的网络结果是 HTTP 200 + x-codex-turn-state。原始文章把 292/312描述成自定义响应码，而当前实现和后续社区项目实际按“头部值长度与块数”工作，两者不能混为一谈。

外层解析目前只能读出：

  • 第 1 字节必须是 0x80；
  • 第 2–9 字节按大端整数解释为签发时间；
  • 余下部分必须满足 57 + 16 × blocks；
  • 完整值可以做指纹和原样回放，但内容本身不可读。

因此不能安全地把 780 截短成 292。它是不透明且很可能带完整性保护的状态值；任何裁剪或拼接都没有有效性依据。

2. 当前实现的完整流程

1 · 捕获Surge MITM 匹配 Responses URL，并读取请求头与 JSON 请求体。
2 · 识别按请求头、路由提示、请求体顺序识别实际模型，组成“账号 + 模型”缓存键。
3 · 采集没有可用值时，用同一认证和模型发送 iPhone 质量探针，可单独指定住宅 IP / SOCKS5 出口；默认最多换 3 次出口。
4 · 校验与注入仅接纳 HTTP 200、完整 SSE、回答 iPhone 17 且 state 外层结构与时间有效的值；随后写入请求头。
5 · 观测响应脚本记录状态、长度、退避和历史；面板显示最近结果。

缓存替换规则

  • 只有通过全部校验的新 state 才会替换缓存。
  • 400、429、网络错误、非 iPhone 17 回答或缺少/无效 state 都不会覆盖仍有效的旧值。
  • 进入续期窗口后，正式请求会先等探针；探针失败时，只要旧值尚未过期，仍继续使用旧值。
  • 旧值过期且采集失败时，正式请求普通放行，不注入 state。
  • 同一账号一次只允许一个模型探针运行；其他模型请求会先普通放行。

blocks 10 旧版长度分类参数；保留给兼容函数和诊断 必须大于 0；当前在线质量路径不再用它决定是否收票 修改该值不会绕过 iPhone 17 质量闸门；后续可在确认无人依赖旧接口后删除
ttl 300 秒 从 state 内部签发时间起计算名义寿命 最小 120 秒；实际过期点为 issuedAt + ttl - 30 本地 TTL 不能延长服务端真实有效性；依赖内部时间字段语义保持不变
renew 60 秒 到期前多少秒进入续期窗口 最小 30 秒；默认在剩余约 1 分钟时续期 它不是“每隔多久续期”。若 renew ≥ ttl，代码会改为约 ttl/3
cooldown 300 秒 一般探针失败后的冷却 最小 30 秒 HTTP 200 但质量未通过时会很快允许下一批探针；网络无响应通常缩短为最多 30 秒，因此不是所有失败都等 5 分钟
timeout 25 秒 内部探针的网络超时，代码名为 probeTimeout 必须大于 0；探针锁额外保留 5 秒 与 Surge 脚本行上的 timeout=90/10/5 不是同一参数；太短会在完整 SSE 到达前失败
probe_attempts 3 一批质量采集最多尝试的住宅出口次数 仅接受 1–8 的整数；每次重新解析探针策略并可生成新的 1024Proxy 会话 尝试次数越多，延迟、额度消耗和 429 风险越高；三次都失败后正式请求未验证放行
retry_base 2 秒 正式请求 429 的指数退避起点 最小 1 秒；序列为 base × 2n-1 只调度客户端之后发起的重试，不能无损重放已经失败的流式请求
retry_max 60 秒 本地 429 等待上限 不得小于当前 retry_base 服务端更长的 Retry-After 仍会回写给客户端，但本地状态等待最多为该上限；设置超过请求脚本 90 秒执行超时可能失效
force_http 1 / true 中止匹配的 WebSocket Upgrade，让 Codex 回退 HTTP/SSE 只有精确值 0 或 false 会关闭 依赖客户端确实会回退；可能显示“Handshake not finished”，也可能直接中断。它放弃了官方优先发展的 WebSocket 路径

参数通过 URL 查询串形式的 argument=... 解析。未知参数被忽略，重复参数以后一个有效值为准；畸形百分号编码会让 decodeURIComponent 抛错并使本次脚本失效。

  2. 同一持久化键中的原始 socks5,... / socks5-tls,... 描述符；
  3. 同一持久化键中的单个命名策略；
  4. policy 参数；
  5. Surge 当前规则。
路由项行为限制

7. 状态、时间与失败处理

条件当前代码行为默认等待
HTTP 200 + 完整 SSE + iPhone 17 + 有效 state保存并可在同一正式请求中注入直到续期窗口
HTTP 200 + iPhone 16/15/无法判定拒绝，不替换旧缓存；批内继续换出口批次结束后 1 秒即可允许下一批
网络错误 / 无状态拒绝并普通放行30 秒
400 / 5xx 等一般状态拒绝并普通放行cooldown，默认 300 秒
401 / 403长冷却，避免持续撞认证/权限ttl，默认 300 秒
探针 429记录账号级限流，同时延后下次探针至少 cooldown，并尊重更长的服务端 Retry-After
正式请求 429回写 Retry-After；挂起客户端下一次自动重试2、4、8、16、32、60 秒，或服务端值

正式请求的 429 不能由 Surge JavaScript 无损“接管并重放”：响应脚本没有原始请求正文，且当前配置不缓冲完整流式响应。代码只延迟客户端自己发起的后续重试；客户端重试耗尽后仍会显示 429。

9. 已确认的实现边界

质量闸门已落地 probeBody() 发送固定 iPhone 问题，回调拼接 SSE 输出并只接受 iPhone 17。每批默认最多尝试 3 次；全部失败且没有未过期缓存时，正式请求会明确记录为“未验证放行”。
  • 跨 turn 复用：CSSS 的核心行为与当前官方客户端的 turn 生命周期约定冲突。它可以发送该头，但不等于服务端承诺支持。
  • 质量规则是项目约定：iPhone 回答可作为本项目的黑盒验收信号，但不是 OpenAI 发布的模型身份字段。
  • 面板不是分模型仪表盘：lastProbe 是全局一条，面板选择一个“最新/可用”条目；多模型同时使用时可能把不同模型的状态并排展示。
  • 旧缓存迁移：历史条目可能没有新版本加入的 model 字段，模型仍存在于内部键中，但面板不一定显示。
  • 正常请求选路：policy 与专用 SOCKS5 只影响采集探针；正常 Codex 请求继续走 Surge 规则。
  • 正常响应不能补做质量判定：响应脚本不缓冲 SSE 正文，只有隐藏探针能把回答与 state 绑定后写入质量缓存。
  • API 通道差异：同一脚本同时匹配 ChatGPT Codex 后端和 OpenAI /v1/responses，但两者认证、模型权限和 state 行为不保证一致。

11. 降质测试方法

此前形成的业务验收规则仍可作为用户定义的结果指标：

  • 回答 iPhone 17 系列：按既定规则记为正常 GPT-6；
  • 回答 iPhone 16 系列：记为路由到 GPT-5.6 Luna；
  • 回答 iPhone 15 系列：记为更严重降质。

有效测试单位必须是“全新会话”，不能在固定会话里连续问三次。建议每个条件至少 5 个新会话，并随机交错“注入/不注入”，同时记录模型、出口、请求时间、是否实际注入、请求 state 指纹、响应长度与块数。这样可以避免先发生服务端路由变化、再切开关造成假阳性。

这个测试回答的是“最终体验有没有变化” 它可以按既定规则判定降质结果；它不能从协议层解释 OpenAI 内部为何路由，也不能单独证明是 state、IP、session-id、负载或账号状态中的哪一个变量造成变化。

12. 质量闸门落地后的验证方法

  1. 先核对面板：记录探针模型、住宅出口类型、尝试次数、iPhone 档位、state 长度与是否注入。
  2. 分开测试作用域：比较同一 turn 内回送与新 turn 回送。前者符合官方客户端语义，后者是 CSSS 的实验组。
  3. 再做回答 A/B：每组至少 5 个全新会话，随机交错“已验证注入”和“未验证放行”。
  4. 按模型分别统计：缓存不会跨模型共享；每个模型都必须独立取得 iPhone 17 + 有效 state 的样本。

质量闸门消除了“固定长度就是好票”的依赖，但没有消除跨 turn 回放的实验性质。需要持续验证的是：同模型、同账号下，带有 iPhone 17 质量证据的 state 在新 turn 中是否稳定改善最终体验。

探针回答项目判定当前缓存动作
iPhone 17正常 GPT-6state 外层结构与时间有效时，作为质量通过的候选值
iPhone 16GPT-5.6 Luna 降智拒绝该次 state，不替换已有正常缓存

没有命中上述系列无法判定不写入质量缓存，保留原有值并等待下次探针

按本项目的验收规则，回答本身就是这一次探针是否降智的判定证据。这样即使 state 统一填充为 780，也能用回答区分本次路由质量；长度、块数和指纹退回为关联记录，不再单独决定好坏。

setHeader() 会先删除大小写不同的同名头，再写入缓存值。因此有已验证缓存时，CSSS 不只是“补缺失头”，还会覆盖客户端原本携带的同-turn state；没有可用缓存时则原样放行，不会主动删除客户端的头。

4 · 正式响应以 SSE 流返回OpenAI → Surge → Codex
Response headers
HTTP/1.1 200 OK
Content-Type: text/event-stream
X-Codex-Turn-State: <OPAQUE_STATE_780>
X-Request-ID: <REQUEST_ID>
Cache-Control: no-cache

# Response body continues as an SSE stream.
Representative SSE frames
event: response.created
data: {"type":"response.created", ...}

event: response.output_text.delta
data: {"type":"response.output_text.delta",
       "delta":"..."}

event: response.completed
data: {"type":"response.completed", ...}

# End of this HTTP response body.

response.completed 表示这一条 Responses 调用完成。CSSS 的响应脚本只读取响应头，不缓冲 SSE 正文；它会记录 780/33 blocks，但不会仅凭正式响应头写入质量缓存。

CSSS interaction
if validated cached state is usable:
    overwrite X-Codex-Turn-State with cached state
else:
    preserve the client's existing header

OpenAI Codex source contract:
    same turn  -> replay exact received state
    next turn  -> do not replay old state

这里揭示了核心冲突：官方 state 是 turn-scoped；CSSS 缓存是“账号 + 模型”scoped。缓存命中时，它可能用跨 turn 的已验证旧 state 覆盖本轮客户端刚获得的 state。

判断一次完整 turn 是否结束，应看最终 response.completed（以及工具循环是否还有后续请求），不能把 TCP 断开、WebSocket 重连、关闭 UI 或 thread-id 变化当成同一件事。

当前 780 情况的一句话结论 当前脚本看到 HTTP 200 + state 780 时，会继续检查同一隐藏探针的完整回答。回答 iPhone 17 且 state 结构与时间有效时缓存；回答 iPhone 16/15 或无法判定时拒绝。该逻辑已经自动执行。
